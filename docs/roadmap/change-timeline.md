# Deployment change timeline (v1)

The additive timeline records observed metadata and leads for investigation. A nearby deployment is not a confirmed cause. Collector and ingestion are disabled by default.

## Contracts and identities

`backend/changes.go` defines ChangeEvent v1. Required normalized webhook fields: schema_version=1, event_id (stable upstream delivery identity), cluster_id, namespace, workload, source (`argocd`, `ci`, `kubernetes`), event_type (`deployment`, `configuration_metadata`, `rollout_observed`, `rollout_complete`). Optional metadata: service, resource_uid, source_timestamp, revision, images, previous_images, source_url. Kubernetes requires resource_uid. Revisions and image strings are bounded; unknown fields, including raw `diff`, `data`, and `env`, are rejected. Upstream summaries/evidence claims are discarded. Server-generated IDs hash cluster, namespace, workload, source, event type, resource UID and upstream identity; no credentials are included in logs.

Missing webhook event_id uses a deterministic key including revision/images/source time; producers should always supply stable IDs to distinguish repeated deployments of the same revision. Duplicate delivery returns the original event ID without changing observation time. First observation, upstream event time and first symptom remain distinct. Missing source time is unknown. Source URLs must use HTTPS without credentials, query strings or fragments. Use public revision links, never signed URLs. No arbitrary Git/CI scanning exists.

New incidents retain the Redis incident sequence ID and get a random analysis request ID. Backend forwards incident_id, analysis_id and cluster_id in additive envelope fields. Known clusters scope correlation group keys and alert fingerprints. Existing incidents are not rewritten; cluster labels and stored Deployment ownership are usable fallbacks. Unknown cluster/workload/symptom disables association rather than broadening silently. Legacy alert keys are preserved for unknown clusters. After upgrade, known-cluster alerts use new scoped keys and may start a fresh incident rather than attaching to old unscoped fingerprints; resolve old incidents normally. No historical deployment timestamp is fabricated from incident creation.

## Security and APIs

- `POST /api/v1/changes`: Bearer CHANGE_INGEST_TOKEN; fail closed if feature disabled, Redis unavailable or sanitizer unavailable. A successful response means the event/index transaction completed in Redis, subject to its persistence configuration.
- `POST /api/v1/changes/coverage`: same service authentication, namespace-scoped observation intervals and last success/attempt/status.
- `GET /api/v1/incidents/{id}/changes?offset=0&limit=25`: HTTP Basic TIMELINE_READ_USER / TIMELINE_READ_PASSWORD, independently verified at the backend. Set these to the same admin credentials used by UI nginx, which forwards Authorization. All authenticated users share existing single-admin incident scope; this is not per-team RBAC. X-Auth-User alone is insufficient. Pagination limit 1–100 and offset capped at 10000; source filtering in the UI applies to the current page.

The backend calls the existing HMAC sanitizer with destination `webhook` before persisting metadata, using SANITIZER_URL and SANITIZER_AUTH_SHARED_SECRET. Raw webhook summaries are discarded before that call. No original body is saved on failure. Policies must preserve routing identities (event_id, cluster_id, namespace, workload); a changed identity is rejected. Use consistent identity policy on alert and change producers; resource pseudonymization that changes these fields is unsupported for timeline association. The new sanitizer NetworkPolicy permits same-namespace backend pods. Existing legacy API routes retain their current authorization behavior; new routes do not accept freely supplied actor headers.

## Collector and coverage

Enable enricher CHANGE_COLLECTOR_ENABLED=true, set immutable CLUSTER_ID, explicit CHANGE_COLLECTOR_NAMESPACES (comma-separated, up to 20), CHANGE_BACKEND_URL and CHANGE_INGEST_TOKEN. CLUSTER_ID also labels alerts. Cluster identity must be unique and stable; do not recycle it for a different cluster.

Bounded polling uses existing apps get/list permissions; no RBAC expansion or Secret/ConfigMap reads. Each namespace is limited to 10 pages of 100 Deployment/ReplicaSet objects and 100 new metadata deliveries per sweep, with a 30-second budget. Poll interval 30–3600 seconds (default 60). Only allowlisted image/revision/ownership/rollout status fields are serialized. Deployment snapshots report unknown source time; ReplicaSet creation uses the API creation time and only considers the last 24 hours. A pod's real ReplicaSet owner resolves its Deployment for incident association. A service field is metadata, not a fabricated workload dependency.

Stable UID/generation/phase IDs prevent duplicate records across restarts and failed HTTP retries. Local bounded caches skip unchanged snapshots; the server's Redis deduplication is authoritative. Cache eviction can cause deduplicated reposts. Polling is deliberately simpler than a cluster-wide informer cache and cannot capture updates deleted between polls. Collection caps yield partial coverage and retry on the next poll, not a completeness claim. For very large namespaces with over 100 new observations per sweep, reduce scope; the page/event limit can prevent reaching later objects until earlier observations are acknowledged. Latest status is unavailable after three minutes without a coverage heartbeat. Webhook-only installations have unknown Kubernetes collection coverage. Coverage records preserve first installation time and the current process observation interval; gaps before or across restarts remain unknown, rather than a fabricated history.

## Storage, rollout and rollback

Redis uses `igpt:change:<id>` strings and hashed cluster/namespace/workload sorted-set indexes. Event and index writes/deduplication are atomic Lua operations. CHANGE_RETENTION_DAYS defaults 30, bounded 1–365. Old source events outside retention are refused; events/indexes expire and indexes prune expired time ranges on writes. Queries use CHANGE_LOOKBACK (default 2h, bounded 1m–7d), plus 15m after the earliest alert source start time. No new full-record scans are used. Eviction policy must remain noeviction; enable AOF/replication and back up Redis if history matters. AOF everysec may lose the most recent second on a crash; single-node Redis does not guarantee recovery after disk loss. Existing incident retention is unchanged. Lowering retention applies to new writes and index cleanup; existing event TTLs expire according to their original setting.

1. Create one existing Kubernetes Secret with `change-ingest-token`, `timeline-read-password`, `auth-shared-secret` (actual sanitizer HMAC key). Do not commit it. Set backend `changes.existingSecret` and env CHANGES_ENABLED=true, TIMELINE_READ_USER and SANITIZER_URL.
2. Set enricher `changes.enabled`, `changes.clusterId`, `changes.namespaces`, `changes.existingSecret`, optional `changes.backendUrl` and `changes.pollSeconds` in Helm values. Reuse the service token; alert and timeline cluster identities must match.
3. Validate sanitizer policy, coverage and a test rollout in a limited namespace. UI distinguishes disabled, unknown, partial, no recorded events, query errors and permission denial.
4. To disable: turn off the collector first, then CHANGES_ENABLED. Keep credentials configured if you want authenticated readers to see disabled status. To downgrade, revert backend/UI/enricher binaries; additive keys can remain until TTL. No destructive migration or backfill is required. Do not delete incident history.

Argo CD normalized fixture and application-specific notification example: `docs/fixtures/argocd-change.json` and `docs/fixtures/argocd-notifications.yaml`. Set your deployment namespace/workload/cluster explicitly, register a notification secret token, and allow the controller namespace through NetworkPolicy. Refresh fixture source time for manual tests; retention intentionally rejects old events. Argo CD template rendering in a real controller has not been exercised locally. CI systems can POST the same contract with authenticated service credentials; no claim of native support for every CI system is made.
