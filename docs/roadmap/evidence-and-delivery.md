# Evidence analysis and durable delivery

Enable `DURABLE_ANALYSIS_ENABLED=true` on backend and `DURABLE_CORRELATION_ENABLED=true` on enricher only after deploying compatible worker/backend readers. Both default false. Configure backend `STRUCTURED_WORKER_URL` to worker `/v1/analyze`; set the same random `analysis-service-token` in the existing Secrets referenced by all three charts. Backend `changes.existingSecret` also supplies reader credentials and sanitizer HMAC. Missing token fails closed; no original payload is sent on sanitizer failure. Keep legacy producers in legacy mode during rollout; new-mode ingest requires the service credential. Mixed clusters and batches above 50 alerts are rejected. Basic reader credentials from PR 1 authorize history/evidence/status endpoints using the existing shared-admin access model.

## Schemas and verified output

`investigation_contracts.go` in backend and worker declares matching v1 Evidence, AnalysisInput, AnalysisVersion and DurableJob wire contracts before consumption. Evidence IDs bind incident, alert source/collection timestamps and bounded content. Excerpts are bounded to 2048 bytes (truncated Unicode at a safe boundary); storage sanitization precedes incident/evidence persistence, and worker sanitization precedes external LLM and response boundaries. Evidence remains immutable. Legacy collected context with no recorded query outcome is `unavailable`, not a successful empty query; legacy query collection time stays unknown; enrichment completion is not substituted for it. Later diagnostics can distinguish available, empty, failed, timed_out, disabled and unauthorized results. Alert source start time is not substituted for source-query observation intervals.

Worker system instructions treat evidence/logs/retrieved context as untrusted data and expose no tools. By default the provider is asked for strict JSON text; a bounded JSON code-fence compatibility wrapper is allowed. Optional `STRUCTURED_OUTPUT_MODE=json_object` adds a native JSON response mode. Malformed/extra fields or citations outside the authorized incident input fail, produce a visible retried/terminal job, and cannot attach as verified citations. Confidence is not stored in new analyses. Legacy Markdown remains accessible, and its confidence label explicitly says uncalibrated model self-assessment.

The validated representation includes summary, competing hypotheses with supporting/contradicting IDs, missing information and next checks. Model/provider/prompt versions, start/end time, input IDs, composition hash and optional numeric usage/cost are retained. Missing usage is unknown. Hypotheses stay human-unconfirmed; later explicit resolution confirmation is separate. Telegram summaries use validated fields and the existing sanitizer boundary. Notification failure is recorded without discarding the analysis. Telegram delivery is best-effort with at-least-once attempts: a provider/worker crash after sending but before acknowledgement can duplicate a notification. No exactly-once external guarantee is claimed.

## Queue and handoff

Backend Redis stores job envelope, evidence, requested-analysis pointer and batch idempotency mapping atomically. Existing incident creation may precede scheduling; if scheduling fails, ingest returns 503 and callers retry the same batch. Group ingestion uses an owned expiring Redis lock, and a stored batch mapping avoids new incidents on redelivery after acknowledgment. Acceptance returns 202 with job_id only after scheduling succeeds. A queued incident is visible independently of LLM completion. No TTL is a retry mechanism.

Four consumers per backend replica claim due jobs atomically. Claim sets ownership and a 90-second lease; worker request has 55-second HTTP timeout, worker total deadline is 50 seconds. Worker concurrency is bounded independently. Retry budgets are four attempts with exponential delay; expired leases recover the exact persisted input after a crash. Stale/duplicate owners cannot acknowledge or overwrite immutable results. Every result routes by incident_id and analysis_id from the job; durable mode rejects legacy group-key callbacks (409). Only the latest requested analysis may update the latest-result pointer. Older completions stay in history. Worker results are synchronous acknowledgements rather than fire-and-forget callbacks, eliminating callback-only loss; legacy callbacks continue only when durable mode is off.

Enricher persists correlation deadlines in `igpt:corr:due`. Due hashes are atomically renamed into immutable batch hashes; arrivals after that operation enter a new pending hash. Delivery leases and stable X-IncidentGPT-Batch-ID allow retries without another incoming alert. Backend acceptance acknowledges the snapshot; it never deletes a newer pending hash. After eight attempts, failed batches remain in `igpt:corr:dead` with metadata `status=dead_letter`; operators can inspect retained safe metadata in Redis. The current UI surfaces analysis dead letters, not a full correlation queue administration screen. Redis-unavailable/capacity failures return 503 to Alertmanager while raw Telegram visibility is attempted; they do not claim durable acceptance. Legacy process timers remain only in disabled compatibility mode.

## APIs and operations

- `GET /api/v1/incidents/{id}/analyses?offset=0&limit=25`: immutable versions, latest pointer and latest 25 jobs. Maximum 100 versions per page.
- `GET /api/v1/incidents/{id}/evidence/{evidence_id}`: verifies incident ownership independently of the citation.
- `GET /api/v1/jobs/metrics`: pending jobs, oldest pending age, overdue scheduling time, retry/failure/completion counters and observed analysis latency sum/sample count. Analysis timestamps provide actual provider latency. This is scheduling overdue time, not an invented incident recovery metric.
- Worker `POST /v1/analyze`: service token, bounded input/result, citations validated twice.

Redis uses existing infrastructure and requires noeviction, persistent volumes and AOF/replication suited to the deployment. AOF everysec can lose the latest second; single-node disk loss is unrecoverable without backup. Incident, evidence, job, analysis and ingest-idempotency records currently follow the existing incident retention policy: no automatic deletion. Include all `igpt:*` keys in backups and capacity planning. Do not purge an evidence record while referenced by a retained analysis. Pending batches have no TTL and require monitoring; dead letters remain for operator inspection. Cross-slot Redis Cluster is unsupported by these multi-key atomic scripts; use the current single-primary Redis deployment or an equivalent non-cluster endpoint.

Rollout: deploy compatible worker, backend and UI; configure Secrets and credentials; enable backend durable mode, then enricher durable correlation. Existing legacy buffered `grp:*` keys are not automatically backfilled: drain legacy correlation before enabling, or keep one legacy deployment until those batches finish. Rollback: stop new durable ingest/correlation, drain or pause pending jobs, retain Redis data, then downgrade. Old binaries do not consume new jobs, so reverting without draining leaves work pending; it must be resumed with a compatible consumer. Basic incident visibility and legacy Markdown remain available.

## Validation environment

`deploy/test-compose.yaml` supplies disposable Redis and pinned Go test images with deterministic fake providers. Run each service in the `incidentgpt-regression` project: `docker compose -p incidentgpt-regression -f deploy/test-compose.yaml run --rm backend-tests`, `enricher-tests`, `worker-tests`. Never point integration fixture environment variables at production Redis; fixtures reset their dedicated queue keys. Host-only tests skip Redis integration unless INCIDENTGPT_TEST_REDIS_ADDR is explicitly set. CI supplies Redis so integration tests run there. Tests cover lease recovery, fencing, duplicate scheduling/acknowledgement, stale results, out-of-input citations, sanitizer failure, atomic snapshot handoff and retry without a new alert.
